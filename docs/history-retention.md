# 历史保留与消除空轮次（最小版）

**先改 personal-agent 的触发方式。** 最近一天约 3,000 轮，按本人的业务口径，master 3 轮、github-pr 5 轮真正推进了事情。先把大量“到点才来看一眼”改为“有事才入队”。每少一次领取和回执，也少一批执行中的心跳与租约事实。独立在线心跳仍会产生。引擎只加一件事：用完整投影做检查点，把已封存的 facts 移到离线文件，平时从检查点重放短尾段。

取消原设计中独立改造上线预检的 PR。personal-agent 已开的 #250 已处理“超时是未完成验证”和“回滚不再重放”。接上检查点后，保留一次候选兼容判定即可。不开在线归档查询，不拆冷热投影，不建代次系统或候选／回退双向证明。wechat-scan 每两分钟轮询、一天 562 轮，归已有 #249 删除，避免重复派工。

**派工入口。** 优先复用已有事件、later、通知函数和 Windows 计划任务。需要周期性判空的本地检查共用一个 personal-agent 入口，在恢复或启动时也运行一次；运维检查不得依赖它所监测的 runner。只读业务表的活动行、未确认动作、版本与下次期限，不能每分钟重跑全量 collect，也不能用整个 hub.db 或 WAL 的修改时间作触发器。对仍需领取的工作使用稳定业务键，取得事件 ACK 才推进游标；执行失败继续走现有重试。切换原 cron 时先排清已入队项，保持规则名和事项归属。maintenance.mjs 现按 schedule.tick 的 id 分流且默认会测内存，新触发必须显式分流；付款控制器也要保留其来源和回答校验。

本地入口每条规则覆盖写最近检查时间、结论和错误。system-map --live 用它区分“已停用、检查健康、检查失败、未报到”；真实 run 和近七天失败数按规则增量读取，旧游标失效时从现存投影重建。看板用相同的业务变化更新受影响事项。样本中 286 次运维回执都报告“机器排队检查或告知未完成”，不能因为取消 hub 轮次就把该分项标为健康。这些改动均在 personal-agent。复核入口为 autoloop/rules.json、docs/系统地图.md、autoloop/bin/{maintenance,worker-queue-health,card-lifecycle,ci-box-sync,main-pc-sync}.mjs 以及 autoloop/plugins/{progress,board,payment-capture,dev-pipeline}。

## 引擎只截断 facts 前缀

在一致的 SQLite 副本上选已提交的 **seq N**。生成一份独立只读检查点，保存全部 projections、projection_meta 的 seq、next 和格式、待投递索引等恢复所需状态。编号高水位从 next 取；旧 run、event、关联、卡片、原回答、通道 ref、timer、各版配置和去重键全部保留。只归档上次边界到 N 的原始 facts，按原序写压缩文件，记录库身份、起止 seq、条数和摘要，沿用原库的私有文件权限。旧的 projection_refs 只服务历史解释，可随前缀裁去；离线重放原 facts 可以重建它们。工作库保有完整当前投影和 N 之后的 facts 与解释索引。

先落盘并核验归档、检查点（文件摘要、序号连续、条数吻合），再用一个 SQLite 写事务核对原边界、登记检查点并移走前缀。中途失败仍能用旧边界重试；期间新提交的 seq > N 完整留下。刚截断、尾表为空时，commit 用 N 作日志末尾，下一条从 N+1 开始。启动沿用有效的当前投影；重建从检查点的状态继续 evolve，不能对一张空投影只喂尾段。周期整理提前做；完整检查点的复制和文件校验放在停服前，停服后只核对基点、最终水位和新增事实。上线可处理的尾段建议先取 **2,048 条或 4 MiB**，完整事务为界。超预算就保留旧服务、先做检查点，超时沿用 #250 的“未完成验证”。

检查点记录自己的文件格式、事实版本及生成时的 projection_meta.format。候选必须支持该格式，并实际从副本打开检查点、校验并应用连续尾段，不加载可写生产 runtime。最小版按严格匹配处理投影指纹（含实现和主密钥身份）。指纹改变时，先在维护窗口外用候选从**离线归档 + 尾段**生成匹配检查点；缺文件、未知版本、数据损坏均不得当成空库。相同引擎、相同输入的完整重放和检查点重放逐行比较所有逻辑投影、seq、next、pending，解释索引只比较保留区间；再核对重复事件／回执、回答续跑和定时到期。这样编号、业务效果、访问权限都有验证依据。

**在线历史契约（由引擎 PR 同步写入 `docs/protocol.md`）**

归档包含 seq ≤ N 的事实，仅供离线审计和人工查阅。鉴权后，`/v1/stream` 未指定游标时从 N 续读；显式 after 或 Last-Event-ID 等于 N，从 N+1 发，早于 N 返回 **HTTP 410** 和 `{"error":"history_archived","checkpoint_seq":N}`。慢订阅被轮转追过时结束流，重连按同一规则处理，不能静默跳号。N=0 的旧库维持从零读取。对检查点时已存在的 run 请求 why，同样返回 410；新 run 的 why 只解释保留区间，并标明起点 N，即使沿用旧规则。未知 run 仍为 404。当前状态、活跃事项、卡片与投递继续用完整投影；在线历史分页只列检查点后新建的轮次，以 N 时的 run 编号高水位识别过期 before 并返回 410（run ID 与 seq 分开）。personal-agent 已核实没有依赖从零订阅或跨界 why 的调用方。CLI／MCP 显示这个历史边界，服务不打开归档文件。

**只截前缀的实测口径。** 上轮 607.16 MB 的一致副本有 313,692 条 facts，原上线命令全量重放 14.45 秒。N=311,644，保留全部业务投影时，工作库 **90.24 MB**，独立检查点 **86.61 MB**；旧 facts 压缩载荷约 21.62 MB，三者约 **198.5 MB**，不含备份、WAL 和文件封装开销。2,048 条尾段实测 0.169～0.202 秒，中位 **0.170 秒**；计入复制完整检查点约 0.20～0.23 秒。这组数字不含服务停启。工作库仍会随真实业务增长；消空转后观察两周，若整理后工作库连续七天超过 **256 MB**，或已有索引的看板／系统图读取在同等负载下连续三天 p95 超过 **2 秒**，再定位是否需要回收旧投影行。
