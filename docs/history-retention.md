# 历史保留、重放与上线检查设计

**建议先在 personal-agent 入队前消掉空轮询，再把已经发生的事实按连续序号归档。** 工作库只留检查点之后的短日志、在办事项和近期历史。上线保留兼容性判定，把全量重放移出停服和回滚路径。看板改读变化和在办事项，这项收益可以先于迁库上线。

这三个改动解决不同的成本。关掉微信扫描后，每两分钟连一轮都不用建。看板即使遇到数万条真实业务记录，每轮也只需处理变化。检查点则能处理过去已经写下、今后仍要解释的事实。保留从零订阅、跨期去重和旧卡片续用，需要在归档中保存历史；可以限制工作库中的历史量和每次上线的检查量，不能同时承诺任意久的完整历史与所有文件合计固定大小。

## 副本告诉了我们什么

2026-11-18 22:33（台北），用 SQLite backup 从 `hub.db` 的 `mode=ro`、`query_only=ON` 连接取得一致副本，包含 WAL 中已提交的事务，导出用时 1.31 秒。下列 MB 均为十进制。引擎为 `390ec6d`，personal-agent 为 `07f7930`，Node 为 24.14.0。两份 personal-agent 检出中的上线检查、看板、系统图和开发队列源码相同。

开发队列最能说明为什么不能按回执文字删除。副本有 16,484 份 `nothing` 回执的摘要恰好是“开发任务排队中”，其中 **16,477 份在同一条 finish 事实里还改了 timers**。这条链的主要输入是 `timer.due`；对应开发规则是事件规则。反过来，进度卡 7,003 轮、微信扫描 4,954 轮的终态是 `done`。按一个终态筛选，两个方向都会分错。现行开发控制器已让队首按十分钟复查、出队时唤醒下一项；历史频率不能直接外推。

另一个增长源是在线与租约。162,409 条 `heartbeat` 中，102,519 条同时更新了 `seen`、run 和到期表，7 条还改了卡片。25,284 条 `channelSeen` 只改了 `seen`。因此，即使消除了业务空轮次，原始日志仍需轮转；按类型整批丢心跳会改变“失联／未知”的判断。

## 空轮次应该在哪里消失

| 方案 | 能省下的成本 | 适用范围 |
| --- | --- | --- |
| 来源先检查，有变化才发事件 | 同时省下 event、run、关联、领取、回执和工作进程 | 推荐给能用开关、业务版本、队列状态或下次到期时间判空的规则 |
| 空时只覆盖一行最近状态 | 能回答“检查器还在吗”，每条规则占固定空间 | 配合入队前检查。已发 Job 后才知道为空时，覆盖行无法恢复 claim、回执重试、费用和这轮的效果 |
| 先照常记录，结束后移到归档 | 保留领活、失败重试和审计，缩小工作库 | 用于必须实际执行才知道结果的规则及已有历史。每次运行的开销仍在 |

**预检放在能看见业务状态的来源侧。** 由项目已有的来源进程或定时任务调用；如果仍让 hub 的 cron 领取一个 Job 再做检查，那一轮已经产生。 微信关闭时停用它的周期触发，恢复开关后从已确认游标补读。开发队列在通道释放、回答到达或任务状态改变时用稳定业务键唤醒队首；保留一处面向队列的低频补偿，覆盖“释放成功而唤醒丢失”。进度卡和看板用业务变更序号及真正的下次提醒时间触发，有时间条件的“卡住未动”即使整段没有新事件也要唤醒。支付以来源游标扫描重叠窗口，心跳告警在状态变化或期限到达时入队。不能廉价、可靠判断的检查继续走普通轮次。业务开关、外部文件和网络探测都留在 personal-agent；内核无需运行预检脚本。

每个已改造的检查器以规则身份覆盖一行本地运行状态，保存启停、应检查时刻、最近尝试、最近成功、最近结论与错误。无变化时可以丢掉逐次的时间戳、空摘要和虚构的 run ID；运行状态过期就显示“检查器未报到”。`system-map --live` 分开显示“刚检查过／已停用”和“最近一次真实运行／成功”，原有七天轮数、失败数和费用只计算真实 run。预检故障不推进业务游标，保留错误与重试，持续故障应能被原有告警发现。纯观察状态丢了可以再检查；进度游标关系到漏单，须在中台确认所有事件后才持久化，崩溃后可重读。

来源仍走现有 `POST /v1/events`，同一变化重试使用同一 `(source,id)`，返回原 event 编号和 routed。原生 cron 默认保留时区、夏令时、错过只补最近一次、`rule@时刻` 去重及调度游标；迁到来源的规则要明确接管这些行为并撤下原 cron，在明确的业务水位交接并补读。原生 cron 来源名为 `schedule`，换来源后相同 id 也不会跨来源去重；须排清旧触发或用同一业务侧处理记录挡住重叠。保留原规则名、lane 和 group，核对旧卡的来源权限；已有卡仍需原来源结案的规则先保留原入口，不能放宽 resolve 的同来源检查。未改造的来源、worker、通道和卡片协议照常使用。回执写了 `nothing` 仍可发卡、回答后收尾、续用、resolve、安排或取消 later、发事件、产生 rejected、记录用量；已领取的轮次走完整事务。只有预检确定无需入队的检查才没有业务历史。

**看板要单独治慢读。** 现行 `board/sources.mjs` 已限制部分 run 的规则，但仍把全部 `run_events` 连接到 events；没有本地连接时还会遍历所有 HTTP 历史页。`system-map.mjs` 则取出所有 run 后按规则排序。第一遍在后台建客户端索引，此后用持久 seq 消费变化，对涉及的 run、卡片、工作区及外部任务查明细。游标和索引同事务提交，重启补读；积压分批并显示数据截至何时。系统图按规则维护最近状态和带时间索引的七天计数；引擎 `/v1/state` 自身的 `GROUP BY` 累计值以及今日、滚动七天费用也要用增量汇总和有索引的时间窗口，避免一次短分页暗中扫遍历史。费用保留缺报数、规则时区和原完成时间边界。看板的验收用相同的未结事项与时间跨界样本比较行和卡片，即使新 run 为零也要正确更新。

## 已有历史如何退出工作库

**切连续前缀，保留原事实字节和原序号。** seq N 取已提交事务的末尾。宿主先把至 N 的增量写入私有归档，按 seq 分块压缩（块大小采用与尾段相同的双预算），建立按序号和 `(collection,key,seq)` 找块的索引。原始事实跨文件仍是一条权威日志。检查点记录在 N 恢复所需的状态，工作库随后只保留 N 之后的事实。把旧 facts 拿走却让旧 run 全留在热表，只能得到上表 90.24 MB 的中间结果。逐轮删“没用的 fact”更不合适，一条 tick 能调度多条规则、合并事件、触发 timer 兼做 sweep，一条 finish 能改多个对象。事后猜哪条 fact 属于谁无法得到相同的重放。

工作集先取最近 4,096 个已结束 run（按完成时间、编号排序）和最近 4,096 个 event。额外保留排队、已领取、未知、待回答或投递、未触发 timer、到期和重试等状态，再沿引用保留办理它们所需的行。终态明细、已触发且已处理的 timer 及其关联超出窗口后转入有索引的冷表，老记录仍可按键读取。低量的卡片、回答和配置在本次估算中全留；持续增长时，同样将已结案历史转冷，保留未结事项、各事项当前续用键及在用规则版本的索引。旧卡仍可被重新打开。投影的每个逻辑键只有一个当代值，更新冷行时在同一次 `evolve` 中提升到热层，删除用带代次的删除记录遮住旧值；查询、排序、分页和聚合都按合并后的逻辑键计算。

建议以 **2,048 条或 4 MiB 原文**先到者作为上线可处理的尾段预算，按完整事务切分；运行中提前准备下一检查点，超预算先在旧服务运行时追平。单笔过大则单独封段、提前验证。两条数字是本副本的起始值，可用压测收紧。4,096 是可移走的历史明细的目标，不是待办上限；可转冷的历史明细另设合计 32 MiB 原始 JSON 预算（建议初值，含关联、已结卡片、回答、投递与旧配置），两者先到就转冷；最近窗口可缩短。仍被在办业务固定的行另计，报告其行数和字节数。归档后的点读依靠持久的冷索引，不把所有过去的键再复制一份到工作库。积压、归档介质满或大量未结业务时如实报告实际占用，保住已确认的数据。总磁盘用量包括归档、备份及短期双代；若要永远删除过期归档，需另定去重期限、`stream` 最早游标、`why` 和历史查询的新契约。本方案选择保留这些能力。

| 需要跨边界保住的关系 | 遗漏的直接后果 |
| --- | --- |
| `run_events.run_id/event_id` 为多对多；`events.(source,key)`、routed 与 hops | 队列合并、失败后重派或扇出会丢输入。任意久的来源重发仍需按冷热精确索引返回同一 ACK；内部回答、timer 与来源键碰撞还要找后缀 |
| `cards.run_id / answer_event / workspace_run`；`answers.id` 是回答事件编号，`card_id` 指向卡，回答行保留当时的卡片快照 | 只保存卡的最新选项会改写旧答案。续用、`context.answers/decided`、原会话、旧工作目录和 `why` 都要能查到 |
| `deliveries.(card_id,channel)` 的 ref、版本、退避与放弃状态；`projection_pending` | 可能重复发送、错认回答者／原消息，或漏掉旧消息的更新 |
| `timers.event_id` 为空表示待触发，触发后指向实际事件；timer、run、card 可沿 `workspace_run` 指到更早的 run | 到期唤醒、上下文、恢复目录依赖这些关系。保留 timer 的来源、会话、Agent、key、hops 和规则／lane |
| run 的 `rules_version` 指向配置事实 seq；`config["rules"]` 与各版本、`issued/last_issued/last_result/last_answer`、claim、session | 旧 claim 可恢复，同一 token 的同一结果返回原 rejected，不同结果仍冲突；切规则或恢复后不能给错权限 |
| schedules、seen、due、keys、各集合编号高水位和引用索引 | 已删编号不能复用，已撤销的密钥不能复活，到期与离线时间不能从迁库时刻重算 |

**检查点是可验证的加速副本。** 封面记录库身份、检查点格式版本、N、各编号的 `next`、事实版本集合、冷数据代次、上一个封段摘要，以及内容摘要和行数。内容用 SQLite 保存原始投影 JSON（包括 SQL 视图没暴露的字段）、各版规则、不可变回答、待投递关系和冷热索引边界。派生索引按所属格式保存或从相同状态再建。宿主的 `host_maintenance` 初始化标记、`maintenance.json` 与主密钥随实例备份；从检查点恢复不能开启维护闸门或重签业务凭据。

检查点格式与 `projection_meta.format` 分开管理。今天后者取 `evolve.ts`、`schema.sql`、`credentials.ts`、`runtime.ts` 的内容及主密钥摘要共同计算；一次注释变化也能要求重建，格式相同也不能证明数据未断档。候选引擎有明确支持的事实版本、检查点读法和投影语义版本。仅索引或查询列变化，可以用受支持的逻辑检查点重建新索引。涉及解释旧数据的变化（例如从历次卡片变更派生回答）必须在切换前用候选引擎从归档加尾段完整构建新代；没有无损读法也走这条路。未知事实版本、缺段、摘要错误分别报错，不以改写 format 通过检查。

等价条件为：对同一引擎、主密钥与同一事实前缀，**从零重放至 S** 与 **打开 N 的检查点、读该代冷数据、重放 (N,S]**，其全部投影的键和值、seq、next、引用序列、待投递集合相等。N 处逐项比较成立，之后以同一有序 fact 调同一 `evolve`，相同输入得到相同下一状态。旧检查点绑定其冷数据代次，后来的提升、删除和再封段不能改变该检查点看到的冷行。这要求读取冷行也参与决策和事务，有效删除不会漏到查询中。验收从两种状态再提交同一输入，覆盖跨界去重、恢复 claim、重复回执、旧卡续用／回答、timer 和规则变化，并比对 ACK、产生的事实与下一 Job。不能用行数或抽取最后几条记录代替比较。

归档由宿主创建，内核经注入的存储读取，不引入网络或产品名。新冷行带待发布代号，已经公布的块和旧代可见的行不可就地覆盖。先写并持久化新段、索引和只读检查点，校验范围完整且无重叠，再在同一 SQLite 写事务中校对父代和 head，发布代次并移走已封存行。发布失败仍读旧代，已写未公布的数据可按摘要重用；老快照和正在读 SSE 的连接读完才回收旧代。写入冲突检查要从“热 facts 的 MAX”改为“检查点 N 与已提交尾段的逻辑 head”，包括刚封段、热表为空的情况；`openView` 也须核对游标与代次。日常分批归档复用空页。每轮只处理上次封段之后的事实与新到期的冷明细，一致读视图导出有界工作集；旧冷段及其索引增量追加，避免每轮复制整个归档。首次迁移用新文件换代，避免每次全库 VACUUM。

对外继续支持 `/v1/stream?after=0`、`Last-Event-ID`、`/v1/runs/:id/why` 和 `/v1/state?before=…`。宿主按相同 seq 顺序读归档和尾段，`why` 跨界找原始规则、回执与卡片事实，两条路径都保留本人鉴权和 `safeFact` 过滤。旧游标遇到缺段要返回可诊断的错误，不能从热区第一条假装续上。已有 HTTP 客户端不需换协议。直接对 `hub.db` 执行 `SELECT … FROM facts/projections` 的插件会只看到热区，这是实际的兼容边界。启用前须将看板、系统图、付款／卡片查询、`live.mjs replay-check`、备份和巡检等直接读库者改用完整的只读访问入口，并核对剩余调用方。归档保留与原库相同的私有访问权限。

## 上线判定与回滚

**取消每次停服前后都跑一次全库重放的门槛，保留“新旧两个版本都能打开这个实例”的证据。** 现行 `inspect.mjs replay` 把每条 fact 解析、查 version、复制到内存，再由候选 `rebuild` 解析和应用。它证明这次没有抛错，未比对业务状态。`runner.mjs` 在运行中预检候选、停服备份后用当前检出再查、回滚配置阶段又查，watchdog 也调用预检。健康判定的 `preserved` 还逐条比对备份里的 facts 与收件箱；只加速第一个 replay 会把同样的问题留在回滚或健康阶段。

1. **旧服务运行时准备。** 用候选和可回退版本各自在隔离副本上实际打开检查点，重放并比对结果。首次迁库、逻辑格式有变或缺少已有证明时，在后台做一次全量等价校验。将结果绑定到实例、两个构建 SHA、格式／密钥身份、检查点与冷归档内容摘要、已验证 seq 和该位置的日志摘要。封存的段不可再改，段摘要串联；对老库首次建链的开销留在这一步。复制、全量校验和格式转换都在服务仍可用时完成。
2. **切换时只证明增量。** 固定最后提交的 S，核对证明对应同一实例、代次和已验证前缀，用候选与回退读法实际应用至 S 的剩余事务，校验连续序号、版本和更新的状态。最多处理上述条数与字节预算；连一次读取都无法完成、前缀换代、证据过期、尾段超限时，推迟切换，在运行中的旧版补证。不能只检查 manifest 的版本号、抽样，或在停服窗口复制／哈希整个归档与检查点。保留原有时间预算。
3. **切换后验证服务和数据延续。** `preserved` 用已验证的不可变段身份和有界尾段比对 hub 的前缀，不能把已归档事实误报成消失。收件箱是另一份 SQLite 数据，需独立的备份水位和已验证增量（包括旧 id 的 sent 变更）；若现有版本只能全扫，先后台做全量见证并跟踪变更，不能用 hub 摘要替代。照常核对版本对、健康、规则摘要、维护 ID 和收件处理。超时／锁忙记为“未完成验证”；只有可复现的版本拒绝或语义差异才算“不兼容”，损坏单列。旧版已停时优先恢复已经证实能读取当前数据的版本对，回滚复用证据并补验新增尾段。

成本上限指关键路径检查的**工作量**。这项证明依赖已验证前缀只读、身份可靠；静默介质损坏由后台逐块校验或读取时验摘要发现，检查窗口不会重新读取每个历史字节。归档全量审计与陌生格式转换仍与数据量有关，应能中断并续作。若当前业务工作集很大，预先打开、校验并准备可切换文件；切换只核对身份和增量。任意负载下的 Windows 启动时间没有由此获得硬上限。

## 首次迁移以及副本实验的边界

先升级只读访问入口、备份工具和 runner。当前版与被保留的上一稳定版都必须认识分段布局才能开启写入；旧格式引擎可能把仅有尾段的库当完整库重建。用明确的布局标记、独立代目录和启动器版本门槛阻止这种组合。第一次只在旧服务旁生成新代。以 SQLite backup 取一致起点，在副本上构造归档和检查点，做全量等价校验，再边运行边追尾。备份集覆盖原 hub、收件箱、ops 状态、主密钥、私有配置及维护文件，绑定同一实例和各自水位；验证备份能在隔离目录恢复。新格式以后还须覆盖其引用的全部冷段／代次，备份轮转不能回收仍被引用的文件。

正式窗口按 **drain → claimed/unknown 均清零 → hold → 停所有写者 → 固定 S → 追最后一段 → 切代 → 启动核实 → 同 ID resume** 执行。hold 只拦新领取，回答、事件、回执等仍可能写入，不能把进入 hold 的时刻当成 S。停写覆盖 hub 和直接写相关库的进程；补齐冻结时刻各库的备份增量并核对最终水位，隔离保存可回退的旧代。关闭连接、收妥 WAL，不把旧 WAL/SHM 配给新数据库。用同卷已就绪目录和一次原子代指针切换，保留旧代和维护意图。新代准备未完成就留旧服务运行。首次的数据整理可在运行中的服务旁完成：副本上前缀构建用了 14.10 秒，归档布局、比对与整理另用 12.39 秒。按本次备份 1.31 秒、尾段最多实测 0.150 秒估算，排空和预建在停服前做，**首次预留 30～60 秒服务中断窗口**，其中数据收尾目标 5 秒内；服务停启、句柄释放、收件箱和健康探针须在同机隔离演练计时后确定实际窗口。排空等待单独报告。

指针切换前失败就舍弃未发布代。切换后先核对各库的写水位；确认完全没有新增提交才可切回旧文件。即使尚未 resume，已有回答或入站事件也算新写。已有新写时优先回退程序、保留当前数据；如必须回旧布局，先冻结并备份新代，用原始事实前缀加全部新增尾段重建到旁路，核对 S、收件箱和凭据的最新状态再切换。旧版本不认识新增事实时继续使用兼容版本恢复服务。直接还原迁移前的 607 MB 文件会丢已确认的工作。

**数字如何复核。** 在临时目录的副本上，以现有 `evolve` 从零应用前 311,644 条构造磁盘检查点，用时 14.10 秒。按最多 2,048 条／4 MiB 将原 UTF-8 JSON 加长度前缀、分 153 块用 zlib 级别 6 压缩；逐块解压所得串的 SHA-256 与输入一致。原文 391.70 MB，压缩载荷 21.62 MB，114.23 MB 的归档还包含冷明细、SQLite 页以及编号和去重索引。精简模型额外保留全部卡片／回答、尾段涉及的键、工作区祖先及关联 timer。本次能回看尾段，提前保留了这些键；运行时新尾段必须能从冷层按需取回旧键。实际热区有 4,350 个 run、5,901 个 event、5,739 条关联和 216 个 timer。这解释了实际保留数为什么大于 4,096。

工作库与归档合并后，161,608 条投影及 339,589 条引用同原副本做了双向 SQL 集合差和数量核对，差异均为零。三次从精简检查点重放尾段计时，最后一次另与预期热区逐项比对了投影、refs、pending、事实及投影元数据。原始副本的 seq/next、pending 和尾段也单独核过；实验用独立格式标记。文件大小取整理后的 SQLite 主文件，13.02 MB 不能单列作总成本。估算未计宿主维护行、主密钥派生的卡片查询索引、拟新增的清单／汇总、备份、双代和运行时 WAL。没有读取生产主密钥，也没有启动服务或对外投递。本次 pending 表为空，不能用它证明跨代补送；三次短重放也是同机缓存条件下的数据库计时。跨代并发、强杀、非空 pending、旧版回退和忙时停服留给实现 PR 在隔离实例验收。

## 交付顺序

每行一个 PR。读新格式的能力先发布，实际切库独立启用；前面的收益无需等待后面的迁移。

| 顺序与仓库 | 可独立上线的改动 | 验收标准 |
| --- | --- | --- |
| 1 · personal-agent | 先解除旧布局的停服风险。在线导出一次，候选与回退版在副本完成全量验证，保留各自可追尾的投影。沿用现有引擎的 `evolve` 校验短增量，取消 backup／rollback 阶段的重复全库 replay，区分超时、损坏和版本拒绝 | 人为使全量验证超过 30 秒，旧服务持续可用；就绪后切换／回退只补短尾段。证明限于同一库文件身份、仅追加的写者和连续 seq，期间若换库、恢复备份或无法确认前缀延续则重新在线取证。故意送入未知事实版本仍须拦下 |
| 2 · personal-agent | 来源端消空转，先关停用扫描，改队首唤醒和有可靠输入版本的周期任务；给系统图区分“检查”和“运行” | 连续多个空周期本规则新增 event、run、关联、业务 fact 均为零；打开开关、有新任务、丢一次唤醒、跨提醒时间，均只执行应有工作。没有活动的规则能区分健康、停用与失联 |
| 3 · personal-agent | 看板与系统图改增量及按需读取，移除正常轮询中的全表关联和全页退路 | 用同一份历史比对旧新版业务条目、旧未结卡和七天统计；重启可补读。历史扩大十倍但新增量相同，稳态每轮读取的记录数不随总 run 增长；现场规模看板目标回到 2 秒内 |
| 4 · 引擎 | 增加版本化检查点、连续归档读法、只读检查和逻辑 head；先在旁路生成，默认继续写原布局 | 旧格式原样打开；从零和从不同 N 重放逐项相等；空尾段提交不复用编号。格式变化、损坏、断段、撤销密钥、非空 pending、跨 N 的 SSE／why 均有行为验证，旧实例可继续运行 |
| 5 · personal-agent | 将已有双向证明接入新的检查点／归档读法，统一预检、停服后、回滚、watchdog、preserved 和手工检查；迁完直接查库的消费者及备份恢复 | 相同大历史下切换只读限定尾段；忙或超时能区分待验证，未知版本确实拦下；候选失败可以恢复上一对且保留新回答和 inbox。新旧布局演练均通过后方可标记 runner 支持新布局 |
| 6 · 引擎 | 启用可选的归档轮转、冷明细读取与热窗口，补齐状态汇总；默认不开启物理移除 | 多轮轮转后热历史回到预算；重复事件与回执 ACK、卡片／回答／通道 ref、timer、统计和历史分页与全量基准一致。覆盖封段前后强杀和并发写、慢 SSE 跨代、冷行再打开；按仓库约定跑日志与并发相关验证 |
| 7 · personal-agent | 钉住兼容版本对，交付一次性迁移、恢复和显式启用入口；单实例切换与版本发布分开 | 用当时的新副本演练完整停启，记录最大尾段、三类文件大小和中断时间，演示切换前、切换后已有新写两种回退。实际启用后对账至最终 S、收件箱、维护与服务健康，再释放旧代 |

最大的风险是**热表看起来完整，实际上漏读了冷历史**。它往往先表现为一次旧事件被再次派发，或一张旧卡在错误的会话续跑；服务本身仍可能显示健康。因此物理移除排在双读、全量等价校验和上一稳定版的恢复演练之后。
