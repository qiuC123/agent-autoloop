# Windows 接单线程启动调查

原始偶发停滞的触发原因仍待确认。本次修复的是已经证实的监督缺口：线程未报错、未退出时，`up` 原来没有启动期限和进度心跳，可能一直对外提供 HTTP 却不接活。没有把故障注入当成原始问题的自然复现。

## 自然复现条件

基线 `b1b1beb`，Windows、Node 24.14.0，运行：

```powershell
node --disable-warning=ExperimentalWarning scripts/worker-startup.ts 12 3
node --disable-warning=ExperimentalWarning scripts/worker-startup.ts 100 8
```

每个实例使用随机临时 home、随机回环端口，真实初始化数据库、密钥和配置，再启动 CLI 的 `up`。先查到 `/v1/state`，再等 worker 上线和启动日志；强杀这个 `up`，用同一份临时状态立即重启。每次等待上限 30 秒。并发实例会同时做真实 Windows ACL 初始化和 SQLite IO；没有真实通道、任务、通知、计划任务或业务目录。脚本退出时清理临时数据。

第一批 12 个实例、每实例两次启动：0/24 停滞。第二批 100 个实例、最多 8 个并发、每实例两次启动：0/200 停滞。合计 0/224；这不能证明原始问题已经消失。没有重建下游业务插件、历史任务或整机长期压力，`SHARE_ENV` 竞争和 TypeScript 加载器故障都没有足够证据归因。

## 确定性失败与修复

`tests/worker-startup.test.ts` 通过仅测试进程使用的 preload 注入以下故障，再从进程外验证结果。生产代码没有测试开关，CI 的 Windows job 会通过现有测试发现规则运行它。

- 模块加载永远阻塞：hub 仍可查，旧版 30 秒后仍不退出。
- worker 目录权限准备永远阻塞：同样静默存活。
- 第一次领活成功，第二次请求永远不完成，同时保留一个活动定时器：旧版仍不退出，说明单看事件循环存活不够。
- 权限准备中的真实同步原生子进程等待：普通退出可能跟着被拖住。独立最小实验在 2 秒后调用 `process.exit(1)`，实际约 15.4 秒才退出，恰好等到子进程结束。

上述失败用例先在未改实现上运行并失败。改后在主线程设置 30 秒启动期限；worker 完成初始化后发送 `ready`，实际处理检查、回执、领活和循环的进度发送 `heartbeat`，期限为 120 秒。测试把这两个监督期限缩短到 5 秒，验证超时日志和非零退出；真实原生调用仍没返回时也必须退出。另测持续健康进度、正常断网重试不被误杀，以及线程异常和退出码 0 都让 `up` 非零退出。

修复后另跑第一条压力命令，0/24 停滞；再把子进程的 `TEMP`、`TMP` 指向含中文和空格的临时目录，同样以 3 个实例并发、每实例强杀重启一次补测，0/24 停滞。最终 worker 回归集（启动监督、worker、Windows worker、插件全链）49 项：44 通过、5 个平台条件跳过、0 失败，包含新增的 9 项检查。原有混合大小写 Windows 环境、慢准备时 hub 仍响应、Agent 强杀后恢复和取消检查均通过。

完整 `npm test` 当轮 331 项：322 通过、9 个平台条件跳过、0 失败，包括 20 万步模拟、5040 条卡片路径和 40320 条调度路径。完整检查启动后补充了断联通知前的进度回报和重试回归用例，随后在最终实现上重跑上述 49 项 worker 回归，全部符合预期。

`npm run typecheck`、`npm run format:check` 和 `npm run test:nightly` 通过。nightly 包括 1000 次真实强杀、35/35 有效变异检出（无无效变异）、1000 个同时等待的连接及全部成功应答，以及性能脚本中的 20 万步固定种子模拟；Windows 性能指标保持 `report-only`。

超时采用同步写 stderr 后对当前 PID 发 `SIGKILL`。Windows 实测为非零退出，不等待同步原生调用。没有对进程树发信号，独立托管的 Agent 使用已有恢复约定；卡在原生调用里的辅助子进程不会被这个信号终止。测试记录并清理自己启动的辅助进程。初始化很慢或某个处理步骤真的连续超过期限时也会触发退出，日志区分启动超时与心跳超时。没有改协议字段、环境大小写语义、ACL、密钥、调度、数据格式或计划任务；SECURITY、示例与架构拓扑仍适用。
